# 0.1.3 release validation

## Scope

This release contains the branch-row focus correction and the chat-footer integration described in the 0.1.3 changelog. Release preparation changes version identifiers, internal semver ranges, the workspace lockfile, release/install documentation, and package-local copies of the existing MIT license. It does not change the previously accepted feature logic.

Release preparation is `triage_skip` under the project's version/documentation/generated-artifact exemption. The earlier feature review was same-family; a cross-family review was unavailable. This record does not claim cross-family approval.

## Mechanical checks

- Host and client TypeScript checks passed.
- Vitest: 16 files, 214 tests passed, with coverage enabled.
- Coverage: statements 83.78%, branches 75.64%, functions 86.05%, lines 88.87%.
- Three implementation builds and the four-package artifact/dry-run checks passed.
- All four manifests, internal dependency ranges, and the UI version label are 0.1.3.
- Each final tarball includes a byte-identical copy of the repository's MIT license.
- Tarball file lists exclude source directories, node_modules, environment files and local session data.
- The client extracted from the installed tarball is byte-identical to the release build.

## Installation and runtime boundary

The final four tarballs installed together in a fresh isolated fixture, offline, with lifecycle scripts disabled. All four resolved to 0.1.3. Existing Harness 0.2.2-rc.1 workspace packages supplied the peer environment through a fixture-only symlink. Host, tool and Remote entrypoints imported successfully. This was a package-install/import smoke check, not a clean installation of Harness itself.

An initial package-only fixture correctly reported missing Harness peers. Whole-tree npm enumeration through the linked host fixture also reported extraneous packages/transitive metadata mismatches; it is not recorded as a passing full dependency audit. Direct package resolution, explicit peer entrypoint resolution and actual runtime imports passed.

The final client differs from the desktop build used for the successful real-GUI fork acceptance only in the displayed version string (0.1.2 → 0.1.3). That earlier real-button acceptance verified an editable child prompt, correct lineage, exactly one child, and an unchanged source log. Release preparation did not replace a running production profile or start another GUI server.

## Distribution

The accompanying JSON manifest and SHA256SUMS identify the final four tarballs. Source/tag pushes, GitHub release assets, and npm registry publication are separate actions. This release operation packages and pushes to GitHub; it does not publish to npm.
